# Архитектура проекта Timeline Notifier

Документ описывает внутреннее устройство, архитектурные слои, потоковую модель, протоколы взаимодействия и критические инварианты проекта **Timeline Notifier** (актуально для версии v3.3.0+).

---

## 1. Назначение и концепция

**Timeline Notifier** — сервис и многопользовательский Telegram-бот для студентов УрГПУ (РГППУ). 
Бот в фоновом режиме:
1. Авторизуется в ЭИОС/Timeline университета (`eios.rsvpu.ru` / `timeline.rsvpu.ru`) под учётными данными каждого отдельного студента.
2. Отслеживает появление новых контрольных точек, дедлайнов, оценок и комментариев преподавателей через JSON-API SendGrid.
3. Доставляет персональные уведомления (новые задания, напоминания за 48/24/12 ч, уведомления о смене статуса, долгах).
4. Предоставляет расписание занятий с сайта `uspu.ru` с умным переключением на выходных и карточками пар (`<blockquote>`).
5. Предоставляет утренние дайджесты, студенческие гороскопы и веб-панель управления администратора.

### Ключевые архитектурные свойства:
- **Zero-Sharing (полная изоляция)**: у каждого студента свои зашифрованные учётные данные, своя сессия и свой независимый набор работ (`user_work_item.user_id`).
- **Монолитный однопроцессный рантайм**: бот, планировщик и веб-панель работают в едином процессе Python без внешних брокеров сообщений (Redis, RabbitMQ, Celery).
- **Сверхнизкое потребление ресурсов (Low-Power Max)**: оптимизирован для слабых ARM-устройств (TV Box Allwinner H313/H616, Raspberry Pi) с потреблением RAM < 64–100 МБ.
- **Split Tunneling через sidecar-прокси (`sota-proxy`)**: трафик к Telegram API идёт через VLESS Reality туннель для обхода блокировок в РФ, а трафик к вузовским серверам идёт напрямую (`direct`).

## 4. Потоковая модель и параллелизм

Приложение запускается единым процессом (`python run.py`) и состоит из следующих потоков:

1. **Main Thread (Веб-сервер)**:
   - В production запускает `waitress.serve(app, host=..., port=..., threads=2)`.
   - В dev-режиме запускает Werkzeug.
   - Обрабатывает HTTP-запросы к панели администратора (`/`, `/users/<id>`, `/broadcast`, `/export/ical/<id>`).
2. **Background Thread `bot-polling`**:
   - Метод `TelegramBot.start_polling()` создаёт поток-демон `_poll_loop`.
   - Выполняет Long-Polling Telegram API (`getUpdates`, таймаут 25 с).
   - При обработке тяжёлых пользовательских команд (например, ручная проверка `/check`) запускает асинхронный воркер через `_run_check_async`, чтобы не блокировать обработку входящих сообщений других пользователей.
3. **Background Thread `scheduler` (APScheduler)**:
   - `BackgroundScheduler(timezone='Europe/Moscow')` тикает раз в `SCHEDULER_TICK` (по умолчанию 60 сек).
   - Проверяет необходимость отправки утреннего дайджеста (`send_daily_digest`), вечернего расписания (`send_schedule_notify`) и мониторинга изменений расписания (`check_schedule_changes`).
   - Раз в минуту вызывает `check_all_users()`.
4. **Воркеры `ThreadPoolExecutor`**:
   - `check_all_users()` выбирает список `User.id`, которым пора на проверку (`now - last_check_at >= check_interval`).
   - Задачи распределяются по пулу потоков размером `CHECK_WORKERS` (по умолчанию 4).
   - **User Lock**: каждый пользователь защищён персональным `threading.Lock()` (`_user_lock(user_id)`). Невозможно запустить параллельную проверку одного и того же студента (например, если совпали плановый тик и ручной `/check`).

## 5. Модель данных и база данных (SQLite)

База данных SQLite размещается в `instance/timeline.db`.

### 5.1. Оптимизация для надежности и Flash-памяти (ARM/eMMC)
В `app/__init__.py` зарегистрирован хук SQLAlchemy на событие подключения:
```python
@event.listens_for(Engine, "connect")
def _set_sqlite_pragma(dbapi_connection, connection_record):
    cursor.execute("PRAGMA journal_mode = WAL")       # Запись без блокировки чтения
    cursor.execute("PRAGMA synchronous = NORMAL")     # Снижение нагрузки на диск без риска коррупции
    cursor.execute("PRAGMA foreign_keys = ON")        # Каскадное удаление
    cursor.execute("PRAGMA busy_timeout = 5000")      # Ожидание при конкурирующей записи до 5 сек
```

### 5.3. Механизм автомиграций (`_auto_migrate`)
Чтобы не усложнять проект миграциями Alembic, в `app/__init__.py` реализован безопасный модуль `_auto_migrate()`. При старте приложения он запрашивает `PRAGMA table_info(...)` для каждой таблицы и добавляет отсутствующие столбцы через `ALTER TABLE ADD COLUMN`. Это позволяет обновлять проект через `git pull` без риска потери данных.

## 6. Безопасность и криптография

1. **Шифрование паролей ЭИОС (`app/security.py`)**:
   - Пароли студентов сохраняются в БД исключительно в зашифрованном виде.
   - Используется симметричный алгоритм **Fernet** (AES-128-CBC + HMAC-SHA256).
   - Ключ вычисляется как `SHA-256(CRED_KEY)`.
   - Зашифрованное значение имеет префикс `enc:v1:<token>`.
   - При отсутствии библиотеки `cryptography` используется обратимая обфускация `obf:v1:<base64(xor)>`.
   - **Инвариант**: `CRED_KEY` нельзя менять после регистрации пользователей, иначе пароли станут нерасшифровываемыми.
2. **Защита в Telegram**:
   - Когда пользователь вводит пароль боту, сообщение мгновенно удаляется из чата (`delete_message(chat_id, message_id)`), исключая сохранение пароля в истории переписки клиента.
3. **Защита веб-панели**:
   - HTTP Basic Auth с логином `ADMIN_USER` и паролем `ADMIN_PASSWORD`.
   - Подпись сессий Flask через `SECRET_KEY`.
   - Защитные заголовки: `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Content-Security-Policy`.

## 7. Парсинг и интеграция с внешними системами

### 7.1. Авторизация в ЭИОС (`app/parser/auth.py`)
- **OAuth цепочка**: 
  1. `GET https://eios.rsvpu.ru/Account/Login` -> следует по редиректам до `https://timeline.rsvpu.ru/Account/OAuthLogin?...`.
  2. Парсит HTML формы входа через BeautifulSoup, извлекает скрытые токены (`__RequestVerificationToken`).
  3. `POST` с заголовками `Referer` и `Origin` на `form.action`.
  4. Проверка сессии: `GET /StudentWork/Send`.
- **Повторное использование сессий**:
  - Куки сессии сохраняются в `bot_user.session_cookies`.
  - Перед повторным логином вызывается быстрый метод `is_session_alive()`. Если сессия жива, полный OAuth-вход пропускается, что ускоряет проверку до ~0.5 с и исключает бан по частоте входов.
- **Классификация ошибок авторизации (`TimelineAuth.reason`)**:
  - `REASON_REJECTED`: неверный логин/пароль -> запрос повторного ввода `/login`.
  - `REASON_NETWORK`: сбои связи / таймаут -> тихий повтор (`LOGIN_ATTEMPTS = 3`). Пользователь не беспокоится, пока `fail_streak < 3`.
  - `REASON_SITE_CHANGED`: изменилась верстка формы -> оповещение администратора.
  - `REASON_FLOW`: сбой редиректов сессии -> автоматическая очистка cookies.

### 7.2. Парсер работ SendGrid (`app/parser/scraper.py`)
- Запрашивает `/StudentWork/Send`, определяет активный семестр (`_detect_semester_id` из `<select name="SemesterId">`).
- Обращается к AJAX эндпоинту таблицы jqGrid: `GET /StudentWork/SendGrid?semesterId=...&rows=100`.
- Извлекает полные данные: сроки, темы, описания заданий, рецензии, баллы.
- Нормализует дедлайн из формата ASP.NET `/Date(1788721199000)/` в локальную дату Москвы (`Europe/Moscow`).
- Автоопределяет группу студента через регулярное выражение `\(([-А-Яа-яA-Za-z0-9 ]+)\)$` из названия дисциплины.

### 7.3. Парсер расписания (`app/parser/schedule.py`)
- Источник: `https://uspu.ru/ajax/rasp.php`.
- In-memory кэш на 2 часа (`CACHE_TTL_SECONDS = 7200`) для снижения нагрузки на сеть и CPU.
- **Smart Week**: в субботу и воскресенье навигация по умолчанию автоматически переключается на расписание следующей учебной недели.
- Оформление через блоки цитат `<blockquote>` с разделением времени, типа занятия, предмета, преподавателя и аудитории.

## 8. Бизнес-логика, алерты и планировщик (`app/scheduler/jobs.py`, `app/services.py`)

### 8.1. Правила иммунитета к просрочке (`is_work_overdue`)
Работа считается просроченной **только если**:
1. Статус равен `''` или `'Не отправлена'`.
2. Флаги `PointAccepted` и `WorkChecked` равны `False`.
3. Статус не входит в `COMPLETED_STATUSES` (`Зачтена`, `Проверена`, `Отправлена`).
4. Дедлайн наступил (`deadline < now`).

*Фильтрация старых долгов*: просроченные работы с дедлайном старше 5 дней скрываются из вкладки `/overdue` и не вызывают постоянных алертов, но остаются в полном списке `/status`.

### 8.2. Жизненный цикл проверки пользователя (`check_user`)
1. Захват блокировки пользователя `_user_lock(user_id)`.
2. Попытка входа по сохранённым кукам -> при неудаче полный OAuth логин.
3. Получение актуальных работ из `SendGrid`.
4. Сравнение с записями в БД:
   - **Новая работа**: сохранение в БД, отправка уведомления студенту.
   - **Изменение статуса / баллов / рецензии**: обновление в БД, отправка уведомления.
   - **Напоминания о дедлайне**:
     - Окно 48 часов: если до дедлайна <= 48 ч и `reminder_48_sent == False` -> отправка, взвод флага.
     - Окно 24 часа: если <= 24 ч и `reminder_24_sent == False` -> отправка, взвод флага.
     - Окно 12 часов: если <= 12 ч и `reminder_12_sent == False` -> отправка, взвод флага.
     - Просрочка: если дедлайн прошел и `overdue_sent == False` -> отправка, взвод флага.
   - **Удаление работ**: если работа пропала из ведомости вуза, она удаляется из БД.
5. При успехе: `fail_streak = 0`, обновление `last_check_at`.

### 8.3. Подавление ложных тревог (`fail_streak`)
Если сайт университета временно недоступен или разорвал соединение (ошибка `network`), сервис не спамит студенту. Ошибка отображается в интерфейсе и шлётся админу только если подряд произошло 3 и более сбоев (`fail_streak >= 3`, пороги 3, 10, 30).

## 9. Сетевая топология и SotaProxy

В РФ доступ к `api.telegram.org` нестабилен из-за блокировок, однако обращение к университетским ресурсам (`rsvpu.ru`) через зарубежные VPN часто блокируется защитой вуза.

Для решения этой проблемы в `docker-compose.yml` встроен сайдкар **`sota-proxy`**:
- Контейнер собирается из `deploy/sota-proxy/Dockerfile` (Alpine + Sing-box + Python).
- Скрипт `run_sota.py` через ключ `SOTAVPN_KEY` получает актуальные параметры ноды VLESS Reality + Vision.
- Генерирует конфигурацию `sing-box` со сплит-маршрутизацией (Split Tunneling):
  - Правило `domain_suffix: ["api.telegram.org", "t.me"]` -> уходит в `vless-out`.
  - Правило `domain_suffix: ["rsvpu.ru", "uspu.ru"]` -> уходит в `direct`.
- Предоставляет SOCKS5-инбаунд на порту `1080` внутри сети Docker (`sota-proxy:1080`).
- Основной контейнер `bot` подключается через `TELEGRAM_PROXY=socks5h://sota-proxy:1080`.
- Порт 1080 намеренно не публикуется на хост, исключая конфликты портов на сервере.

## 10. Ключевые операционные инварианты

1. **Инвариант пересборки Docker (Deploy Invariant, см. `AGENTS.md`)**:
   Исходный код (`app/`, `run.py`) запекается в Docker-образ на этапе сборки (`COPY . .`). В тома монтируется исключительно каталог базы данных и логов (`./instance:/app/instance`). Live bind-mount кода отсутствует.
   - **СТРОГО ЗАПРЕЩЕНО** использовать `docker compose restart` для применения изменений в Python-коде, шаблонах или статических файлах.
   - При любых изменениях кода **ВСЕГДА** выполнять пересборку:
     ```bash
     docker compose up -d --build bot
     ```
2. **Инвариант единственного поллера (Single Poller Invariant)**:
   Один Telegram Bot Token может опрашиваться ровно одним процессом.
   - Запрещено масштабировать сервис: `docker compose up --scale bot=2` вызовет `409 Conflict: terminated by other getUpdates request`.
   - Запрещено запускать локальный `python run.py` с тем же токеном, что и на сервере.
3. **Инвариант неизменности `CRED_KEY`**:
   `CRED_KEY` в `.env` генерируется один раз до старта регистрации. Изменение ключа приводит к безвозвратной потере доступа к сохранённым паролям студентов.
4. **Инвариант часового пояса (Timezone Invariant)**:
   В контейнере и системе **обязателен** часовой пояс `Europe/Moscow` (`TZ=Europe/Moscow`). Дедлайны Timeline не содержат информации о таймзоне и парсятся как локальное время Екатеринбурга/Москвы.
5. **Права на папку `instance/`**:
   Контейнер запускается от пользователя `APP_UID:APP_GID` (по умолчанию 1000:1000). Каталог `instance/` на хосте должен принадлежать этому же пользователю во избежание ошибки `unable to open database file`.

## 11. Тестирование и верификация

Тестирование логики осуществляется с помощью детерминированного скрипта без обращения к внешней сети:
```bash
# Запуск из виртуального окружения:
.\venv\Scripts\python.exe tests\smoke_test.py    # Windows PowerShell
python tests/smoke_test.py                      # Linux / Docker
```

Что проверяет `smoke_test.py`:
- Онбординг и валидацию логина/пароля через mock-объекты.
- Полную изоляцию данных между несколькими пользователями (`CHAT_A`, `CHAT_B`).
- Логику окон напоминаний (48/24/12 ч) и расчет просрочки.
- Корректность работы автомиграций SQLite.
- Целостность генератора шуток (все 400 шуток в 39 категориях) и сидирование `random.seed(20260930)`.
- Роуты админ-панели и экспорт iCalendar.
